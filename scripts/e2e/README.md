# Dedicated local DVC acceptance infrastructure

This harness uses the real Next application and a separately owned local Supabase stack. It never starts, resets, migrates, seeds, or stops Supabase. Loopback alone is insufficient proof of isolation: preflight checks exact container IDs, the dedicated CLI project label, running state, shared dedicated network, literal loopback bindings and database routing for Auth/REST/Storage. It rejects remote targets, the normal application port and the default Supabase ports. Container inspection is local metadata verification, not proof that every upstream request is harmless; stack configuration must also disable external providers and substitutes before fixture approval.

Pinned project dependencies: `@playwright/test@1.64.1` (Node >=20), `supabase@3.0.0`. Installations were explicitly approved for M1. Browser downloads and official Supabase images are authorized, but commands do not automatically install or start them. Use `npx --no-install playwright install chromium` when needed. The Supabase CLI may require a dedicated writable CLI home; inspect its installed help before configuring a stack. Never reuse authenticated hosted-project CLI state. Prepare the external QA workdir using supabase/qa.config.example.toml: replace the derived project ID and local-only secret placeholders outside Git, and inspect its loopback network and disabled provider/seed settings before an authorized startup. Never replace the ordinary development config with this template.

## Configuration and commands

Copy `environment.example.json` to the approved evidence directory outside Git, set mode 600 and replace every placeholder with values from the dedicated QA stack. Never copy `.env.local`, hosted keys, or real user data. Export only the path as `DVC_E2E_ENV_FILE`. The project ID is the SHA256-prefix of the repository realpath, so another checkout must derive its own ID. Use a new run UUID for each evidence run. Set `DVC_E2E_ARTIFACT_DIR` to an existing absolute directory within the external QA configuration file’s canonical parent. The root, UUID run directory and writer destinations must remain outside the repository and contain no symlink components beneath that approved parent. Relative paths, traversal and missing artifact roots are rejected; results are stored under the validated run UUID. Avoid screenshots containing secret configuration or private player information.

- `npm run test:e2e:guards`: Node infrastructure unit tests, no application services or data.
- `npm run test:e2e:preflight`: inspect declared local Docker metadata, no writes.
- `npm run test:e2e`: preflight, then one Chromium worker against a new QA-only application process. No CLI overrides are accepted. `reuseExistingServer` is false; an existing server on port3317 is an error. The root playwright.config.mts and tests/e2e/package.json ESM boundary keep configuration and test/helper imports compatible with the .mjs safety modules without changing the application package type. Two approved M1 acceptance tests are implemented in tests/e2e/m1-foundation.spec.ts; their runtime outcome must be reported separately from infrastructure unit checks. They have not been run by the infrastructure implementer. Cancellation reaches the owned Playwright child as SIGINT (its supported teardown signal), while the wrapper retains the original interruption status (130/143). Playwright gracefully stops its owned web-server process with SIGTERM and a ten-second timeout; the runner waits for shutdown and retains a nonzero interrupted result.

The launcher constructs an allowlisted process environment, explicitly clears every current app-owned key before Next loads `.env.local`, and sets the QA keys and URL. Hosted Sheets credentials, contact links, webhook/cache secrets and Vercel settings are blank. Next uses fixed `.next-dvc-e2e` output when `DVC_E2E=1`; ordinary application builds retain their existing output. A generated fixed .dvc-e2e/tsconfig.json outside the Next output directory extends the root config and keeps Next include updates outside tracked tsconfig.json. Next still regenerates the ignored root next-env.d.ts; the launcher records before/after bytes and hashes in external evidence. It deliberately leaves any change for inspection because a normal server may concurrently regenerate that shared file. The dedicated application uses Next development mode so normal `.next` output and production build artifacts are preserved. Trace/video capture is off because authenticated requests may contain sensitive tokens. Screenshots on failure require human inspection before sharing.

## Authentication and coverage boundaries

No production login bypass, role override or special application route is added. The approved local fixture authenticates a synthetic local account through normal GoTrue password grant and store its genuine tokens in the existing encrypted DVC cookie format. The application still validates `/auth/v1/user` and its normal role RPC. This skips the Google login UI/callback and cannot prove Google OAuth works.

**Staff-allowed coverage is blocked:** current `dvc_role` requires a verified Google identity associated with the whitelisted email. A password-authenticated account remains a Player even if a whitelist row exists. Do not forge Google identity records, metadata, claims, or weaken the role function. M1 can check authenticated Player own-allowed and staff-denied behavior using supported local authentication. Staff-allowed acceptance requires an approved supported local OAuth/provider strategy; report it as BLOCKED until available.
